# Decision: 路由器到期后的出口认证与结果提示

Status: implemented

## Problem

未认证时门户可能提供真实出口 IP，却没有真实 MAC。强制要求真实 MAC 会让客户端在提交密码前停止；把 `online_list.result=1` 当作已认证，会掩盖空列表和外网跳转门户的证据。仅按外网是否恢复显示结果，无法区分未提交、被拒绝和门户已接受。

## Decision

本记录部分替代 [桌面认证出口与监控生命周期](2026-10-04-router-maintenance.md) 的真实 MAC 必需规则。`AuthContext` 继续拥有每次刷新得到的出口身份；南京工业大学 `drcom_new` 路由器模式的已知门户，缺少 MAC 或只有门户未知占位值时使用 `000000000000`。真实 MAC 优先；IP 必须有效，页面、探测重定向和身份查询之间的 IP/MAC 冲突及异常格式拒绝提交。不使用本机身份或旧上下文补齐。

`EPortalAPI` 区分 `online_list` 的查询成功码与 `chkstatus` 的认证状态码。列表要求 `list` 为对象数组、`total` 为非负整数且等于记录数，`online_ip` 为有效 IPv4 字符串。只有当前出口的匹配记录证明已认证；完整列表没有当前出口证明需要认证。列表缺失、矛盾或查询失败时自身判定未知；已知南京工业大学路由器协议再请求 `/drcom/chkstatus` 独立核验，对本次响应重新校验出口身份。按学校 `a41.js` 的内核状态语义，`result=0` 表示未认证、`result=1` 表示已认证，不依赖中文消息。内核状态码未知、身份冲突或请求失败时保持未知。明确未认证的列表失败码响应仍可证明离线。外网探测明确跳转已知认证门户时保留证据，不能因查询成功而提前返回。外网探测成功仍是在线的最终依据。

`LoginResult.phase` 由 API 生成，经监控器事件队列传给 GUI；默认 `not_submitted`，尝试认证请求后为 `failed`，门户明确接受后为 `accepted`，外网验证通过或原已在线时为 `online`。验证失败或异常不能把 `accepted` 改成未提交。`success` 继续只代表已验证外网可用；四种阶段对应各自提示。自动认证同样发布登录结果。

运行时字段只在本进程内传递，API、monitor 和 GUI 随同一个 EXE 替换。保存配置和 DPAPI 密码格式不变，移动端与旧 `eportal_api.py` 不消费此字段。原串行工作线程、立即检测、退避、主动注销暂停、错误账号暂停、取消、停止及 mutex 责任保持原决策。

离线诊断由 `NetworkStatus.debug_log` 进入 GUI 和本地监控日志；在线列表只记录结果码类别、计数、条数和判定，内核只记录状态码类别及判定。原始记录、响应中的账号/密码及完整请求 URL 不进入日志；已在线时不增加常规探测日志。

## Alternatives considered

- 一律要求真实 MAC：未认证时身份接口可不返回 MAC，客户端无法启动恢复。
- 使用电脑 MAC 或缓存上次身份：路由器出口不等于电脑，身份变化后可能认证错误出口。
- 查询成功就判已认证：空列表同样可返回成功，造成到期后一直不登录。
- 所有探测失败都认证：已认证但运营商外网故障时反复提交账号。

## Consequences

协议允许客户端以真实出口 IP 和零 MAC 启动到期认证；未知协议没有该例外。严格列表结构与独立内核核验共同避免从不可靠查询推断认证状态；只有所有证据均未知时才等待。未知列表最多增加一次只读内核请求，取消和超时仍归 API/监控器所有。认证接口接受不能保证手机共享或外网恢复，需要独立现场验收。

## Verification

生产 API、监控启动和 Windows Tk 使用模拟 HTTP 覆盖无 MAC 恢复、旧身份不复用、真实 MAC、列表为空/其他出口/匹配/异常、门户重定向、密码错误和认证已接受但外网失败。Windows 构建、真实 EXE 启动/托盘/退出/重启/双入口锁及 SHA256 对照记录于 [EVIDENCE](../../EVIDENCE.md)。只读现场查询确认 `online_ip`、列表及计数结构；用户已于 2026-10-06 确认本版本自动重新认证成功。手机共享、完整的退出后到期重启流程及长时运行尚未分别确认。

## Rollback

正常退出程序后替换旧 EXE，不迁移配置或密码。旧版本仍会拒绝缺少真实 MAC 的路由器认证，不能用旧版验收该修复；恢复网络可使用学校门户。无需数据库、手机或路由器变更。
